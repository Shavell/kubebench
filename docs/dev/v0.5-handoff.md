## 2. Decisions taken

- **Branch**: everything happens on `release/v0.5.0`. `main` stays at
  `acc8149` until the user decides to merge (fast-forward is possible).
  Remote `github` = `git@github.com:Shavell/kube-bench.git`. The Gitea
  `origin` (`gitea@10.103.0.42:apps/kube-bench.git`) has **not** been
  updated.
- **Version**: next release is `0.5.0` (package.json/Chart still say
  0.0.0/0.1.0; bump pending).
- **i18n**: i18next + react-i18next.
  - `en` (fallback) and `tr`.
  - Namespaces: `core` (`src/i18n/locales`), `platform` (`src/core/locales`) and one per plugin (`src/plugins/<id>/locales`, registered via `PluginManifest.locales`).
  - Manifest strings are i18n keys.
  - `nsSeparator: false`.
  - Turkish glossary: see the W1 prompt in `orchestration/w1-foundation.md`.
- **Roles**:
  - global `admin`/`user`;
  - per-cluster assignment `viewer`/`operator`;
  - a cluster `read_only` flag that blocks write/exec for everyone;
  - a cluster `environment` tag;
  - an audit log for write/exec/admin;
  - forced password change for the default admin.
- **Plugins**:
  - Backend plugins are Go packages that register through `init()` and mount under `/api/plugins/<id>/`, with `Detect` per cluster and a plugin-scoped KV.
  - Frontend plugins use `PluginManifest` v2, enabled/available filtering in the registry, plugin-owned data via `definePluginData`.
  - Runtime-loaded external UI plugins (IIFE + `window.KubeBench`).
- **Honest data**: live mode never shows mock data. Mock mode only in dev,
  with `?demo`, or with `VITE_DEMO_MODE=true`.
- **Distribution**:
  - GoReleaser (+nfpm) for binaries, .deb/.rpm and checksums;
  - `install.sh` for `curl | bash`, online and offline;
  - an offline bundle;
  - Helm chart (OCI) + rendered manifests;
  - multi-arch image `ghcr.io/shavell/kube-bench` (the maintainer builds images himself for now);
  - all GitHub workflows `workflow_dispatch` only;
  - Dependabot for npm, gomod, actions and docker.
- **Testing**: the homelab cluster `k3s-homelab` is read-only for agents.
  Creating a local kind cluster was **denied by the auto-mode classifier**
  on the old VM. The user plans to use k3s/k3d on the new VM; see §6.
- **License**: none yet. Packaging leaves license fields empty with a TODO;
  **open question for the user**.

## 6. Test environment on the new VM (k3d/k3s)

The rules change only in one respect: **mutations may be tested against a
disposable local cluster that the session created itself**. The developer's
homelab (`k3s-homelab`) stays read-only.

Suggested setup (run by the user or the session, with permission):

```bash
# k3d (k3s in Docker): 1 server + 1 agent, its own kubeconfig file
k3d cluster create kubebench-e2e --agents 1 --wait --kubeconfig-update-default=false
k3d kubeconfig get kubebench-e2e > /tmp/kubebench-e2e.kubeconfig
export KUBECONFIG=/tmp/kubebench-e2e.kubeconfig

# extras used by the feature tests
kubectl apply -k "https://github.com/argoproj/argo-cd/manifests/crds?ref=stable"   # Argo CD CRDs only
# local-path StorageClass ships with k3s (storage plugin tests)
# metrics-server ships with k3s (metrics tests)
```

Agent rules for that cluster:
- Use only its kubeconfig file. Never touch `~/.kube/config` contexts other than reading the homelab.
- Work in namespaces named `e2e-<feature>` and clean up afterwards.
- Node operations (cordon/drain/taints) only on the agent node, and uncordon at the end.
- Delete the cluster when the session ends (`k3d cluster delete kubebench-e2e`).
