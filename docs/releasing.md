# Releasing KubeBench

## Versioning

KubeBench follows [Semantic Versioning](https://semver.org): `MAJOR.MINOR.PATCH`,
with pre-releases such as `0.6.0-rc.1`. Until 1.0, a minor version may break
APIs, the plugin SDK or configuration; the CHANGELOG says how to migrate.
Tags are `v` + the version (`v0.6.0`).

One version identifies every artifact of a release:

| Where | Field |
|---|---|
| `package.json` | `version` (shown in the UI as `__APP_VERSION__`) |
| `charts/kubebench/Chart.yaml` | `version` and `appVersion` (the chart's default image tag) |
| `CHANGELOG.md` | the `## [X.Y.Z] - YYYY-MM-DD` section |
| `deploy/kubernetes/kubebench.yaml` | the image tag (regenerated by `make manifests`) |
| binaries, packages, image | stamped by the build (`-X main.version`) from the git tag |

Development builds get their version from `scripts/version.sh`:
`git describe` on the latest `v*` tag (`0.6.0-3-gabc1234`, `-dirty` for
uncommitted changes), or `<package.json version>-<sha>` before the first
tag. `make version` prints it. GoReleaser snapshots use
`<next patch>-snapshot-<sha>` (`0.5.1-snapshot-abc1234`).

## CHANGELOG discipline

[`CHANGELOG.md`](../CHANGELOG.md) follows
[Keep a Changelog 1.1](https://keepachangelog.com/en/1.1.0/), and its
sections become the GitHub release notes (`scripts/extract-changelog.sh`).

- Every user-visible change adds a line under `## [Unreleased]`, in the same
  pull request, grouped as Added, Changed, Deprecated, Removed, Fixed or
  Security. Write for users: what changed and what they have to do.
- Breaking changes and upgrade steps go first in their group.
- To release, rename `[Unreleased]` to `[X.Y.Z] - YYYY-MM-DD`, add a new empty
  `[Unreleased]` above it, and update the compare links at the bottom.
  Pre-releases (`X.Y.Z-rc.N`) get a section of their own.

## Cutting a release

### 1. Prepare (pull request)

1. Bump `package.json` (and `package-lock.json` via
   `npm version X.Y.Z --no-git-tag-version`) and `Chart.yaml` `version` +
   `appVersion`.
2. `make manifests` to re-render `deploy/kubernetes/kubebench.yaml`.
3. Date the CHANGELOG section.
4. `scripts/check-release.sh X.Y.Z` must report "ready", and `make test lint chart-lint` must pass.
5. Merge into `main`.

### 2. Release with GitHub Actions

Run the **Release** workflow (Actions > Release > Run workflow) on `main`
with:

| Input | Meaning |
|---|---|
| `version` | `vX.Y.Z`; the tag is created on the selected commit when it does not exist yet, an existing tag is released as it is |
| `prerelease` | mark the GitHub release as a pre-release (versions with `-rc.N` and the like are marked anyway) |
| `push_image` | also push the multi-arch image `ghcr.io/shavell/kubebench:X.Y.Z` (+ `X.Y`, and `latest` for final releases) |
| `push_chart` | also push the chart to `oci://ghcr.io/shavell/charts/kubebench` |

The workflow checks versions and the CHANGELOG (`scripts/check-release.sh`),
runs `make test`, tags, builds the frontend, runs GoReleaser (binaries,
archives, `.deb`/`.rpm`, `checksums.txt`, a **draft** release whose notes are
the CHANGELOG section), attaches the chart `.tgz`, the manifests and
`install.sh`, builds the image tarballs and the offline bundle and uploads
them to the draft. Review the draft on GitHub, then publish it: only
published releases are visible to `install.sh` ("latest") and to users.

The other manual workflows:

- **CI**: frontend, backend, chart, packaging config, shell scripts, workflows.
- **Container image**: build (and optionally push) an image for any ref, tag and platforms.
- **Helm chart**: lint, package and optionally push the chart.
- **CodeQL**: static analysis for Go and TypeScript.

### 3. Or release from a workstation

Needs Go, Node 24, Helm, GoReleaser v2, Docker with buildx, and a GitHub
token with `contents: write` in `GITHUB_TOKEN`:

```bash
scripts/check-release.sh 0.6.0 && make test
git tag -a v0.6.0 -m "KubeBench v0.6.0"
git push origin v0.6.0        # the remote that points at github.com/Shavell/kubebench
mkdir -p build/extra
helm package charts/kubebench --destination build/extra
cp deploy/kubernetes/kubebench.yaml install.sh build/extra/
scripts/extract-changelog.sh 0.6.0 >build/release-notes.md
goreleaser release --clean --release-notes build/release-notes.md
```

Then the images and the bundle:

```bash
for arch in amd64 arm64; do
  docker buildx build --platform "linux/$arch" \
    --build-arg VERSION=0.6.0 --build-arg COMMIT="$(git rev-parse --short HEAD)" \
    --build-arg DATE="$(git log -1 --format=%cI)" -t ghcr.io/shavell/kubebench:0.6.0 \
    --output "type=docker,dest=build/kubebench_0.6.0_linux_$arch.tar" .
done
scripts/offline-bundle.sh 0.6.0 --chart build/extra/kubebench-0.6.0.tgz \
  --image-tar build/kubebench_0.6.0_linux_amd64.tar --image-tar build/kubebench_0.6.0_linux_arm64.tar
gh release upload v0.6.0 build/extra/kubebench-offline-0.6.0.tar.gz{,.sha256}
```

### Dry runs

`make snapshot` runs the whole GoReleaser pipeline without a tag or
publishing (output in `build/release/`), `make deb` builds only the
packages, and `make offline-bundle` assembles a bundle from that output.

## What a release contains

| Artifact | Built by |
|---|---|
| `kubebench_<v>_{linux,darwin}_{amd64,arm64}.tar.gz`, `kubebench_<v>_windows_amd64.zip` (binary, LICENSE, README, CHANGELOG, `install.sh`, systemd unit, env file) | GoReleaser |
| `kubebench_<v>_{amd64,arm64}.deb`, `kubebench-<v>-1.{x86_64,aarch64}.rpm` (license in `/usr/share/doc/kubebench/copyright` or `/usr/share/licenses/kubebench/LICENSE`) | GoReleaser (nfpm) |
| `checksums.txt` (SHA-256 of the archives and packages) | GoReleaser |
| `kubebench-<v>.tgz` (Helm chart), `kubebench.yaml` (manifests), `install.sh` | release workflow, via `build/extra/` |
| `kubebench-offline-<v>.tar.gz` + `.sha256` | `scripts/offline-bundle.sh` |
| `ghcr.io/shavell/kubebench:<v>` (linux/amd64, linux/arm64, SBOM and provenance) | release workflow (`push_image`) |
| `oci://ghcr.io/shavell/charts/kubebench:<v>` | release workflow (`push_chart`) |

Every artifact carries the GPL-3.0 text: the archives and the offline
bundle as `LICENSE`, the packages as noted above, the image as `/LICENSE`
and the chart as `charts/kubebench/LICENSE` (a copy that
`scripts/check-release.sh` compares with the repository's).

## Turning CI on

All workflows run only on `workflow_dispatch` for now. Each has its future
triggers commented out right below `on:`; uncomment them to activate:

| Workflow | Trigger to uncomment |
|---|---|
| `ci.yml` | `push` to `main`/`release/**`, `pull_request` |
| `codeql.yml` | `push`, `pull_request`, weekly `schedule` |
| `docker-image.yml` | `push` to `main` (then consider `push: true` for a rolling `main` tag) |
| `helm-chart.yml` | `push` with `paths: charts/**, deploy/**` |
| `release.yml` | `push` of `v*` tags: the version then comes from the tag, and `push_image`/`push_chart` are off unless you change their conditions |

Dependabot (`.github/dependabot.yml`) opens grouped weekly update pull
requests for npm, Go modules, GitHub Actions and the Dockerfile base images
as soon as the file is on the default branch; it does not depend on the
workflow triggers. Once CI runs on pull requests, protect `main` with the CI
jobs as required checks.
