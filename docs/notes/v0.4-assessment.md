# KubeBench v0.4 assessment (2026-11-14)

*This is the original assessment that started the v0.5 work. File:line
references point at commit `acc8149` (v0.4). Its follow-ups are
`docs/design-v0.5.md` and
[`kubelizeme-comparison.md`](kubelizeme-comparison.md).*

Goal: improve KubeBench. KubelizeMe's compiled desktop bundle was used as
the reference (details:
[`kubelizeme-comparison.md`](kubelizeme-comparison.md)).

**Short summary:** KubeBench has strengths KubelizeMe lacks: a multi-user
web architecture, installation inside the cluster, and Prometheus metrics.
For day-to-day operations tooling, however, KubelizeMe is far ahead: a real
terminal, live logs, YAML editing and apply, Helm install and upgrade, and
security auditing. Reading the code also turned up a few problems that
should be fixed first. The most critical are fake data being shown in live
mode and the absence of a permission model.

## 1. Where KubeBench stands apart and should stay that way

| Area | KubeBench | KubelizeMe |
|---|---|---|
| Deployment | Web; single Go binary, installed into the cluster with a Helm chart | Desktop (Tauri), single user |
| Users | Login, sessions, admin/user roles, assigning clusters to users | None |
| Metrics | Discovers Prometheus on its own; history, network and disk charts; allocated resources panel and overcommit marker | metrics-server only |
| Helm and kubectl | Native Go SDK, no local binary needed | Needs the local `helm` CLI and a tool check |
| Architecture | Plugin structure and provider layer, mock mode | Monolithic application |

## 2. What KubelizeMe has and KubeBench lacks

| Area | KubelizeMe | KubeBench (v0.4) |
|---|---|---|
| Terminal | Real PTY (xterm), reconnect, search | One-shot `sh -c`; `cd` is not kept, 20 s timeout |
| Logs | Live stream from multiple Pods via a label selector, previous container, tail setting, save | 300 lines at once, no live follow |
| YAML | Apply, server-side dry-run, diff against live, neat, conflict warning | Generic resources are read-only |
| Operations | Node cordon/drain/taint, force and bulk delete, debug container, port-forward, rollout history and undo, pause/resume, namespace create/delete, label editing | Pod delete, deployment scale/restart |
| Live data | Watch-based cache | Full List on every request; auto-refresh off by default |
| Helm | Install, upgrade with dry-run, repo add/update/search, values diff | List, history, values, rollback, uninstall |
| Security | CIS v1.10 / NSA-CISA / PSS audit, accepted risks in a CRD, CSV/MD/PDF report, RBAC "who can do what", admission policy view | None |
| Visualization | Topology graph, cluster comparison | None |
| Composer | Form-based manifest wizard, templates, apply to multiple clusters | None |
| AI | Claude/OpenAI/Ollama/LM Studio/OpenRouter, permissioned tool calls, MCP, playbooks | None |
| Usability | kubectl-style palette, aliases, namespace pinning, colored cluster groups, **per-context read-only mode**, keyboard table navigation, virtual list for large tables | Has a command palette |

## 3. Problems found in the code (in priority order)

1. **Fake data is shown in live mode.** A user may take made-up data on a production cluster for real.
   - `src/main.tsx:29-41`: if `/api/info` does not answer within 2 seconds or returns any error other than 401, the app silently switches to mock mode (in production builds too).
   - `src/data/api/index.ts:41`: on any error in the metrics query, a fake series is drawn as if it were real.
   - `backend/internal/kube/runtime.go:96`: the permission probe runs in the background. The first `/api/info` call after a backend restart always returns `crds/helm/exec=false`; the Helm and CRD modules show **fake releases** until the page is reloaded.
   - When RBAC denies access, the Helm and CRD modules fall back to mock.
2. **No permission model.** The chart ships with `cluster-admin` by default (`charts/kubebench/values.yaml:24`) and the password `admin/admin` (`values.yaml:13`). The API only checks the session. Anyone with the "user" role can exec into kube-system pods and run `helm uninstall`. The proposed fix is a role per cluster assignment (viewer/operator) or `rest.Config.Impersonate`; an **audit log** is needed as well.
3. **Events are attached to the wrong object.** `backend/internal/kube/resources.go:80` filters only by `involvedObject.name`. The detail view of a Deployment named "web" also shows the events of the Service, Ingress and HPA with the same name. The frontend sends the `kind`, but `src/data/api/index.ts:68` ignores it.
4. **Session security.**
   - The cookie has no `Secure` flag (`backend/internal/api/auth.go:33-40`).
   - No rate limit on login attempts.
   - `POST /api/clusters` can read any file on the server through its `path` parameter (`backend/internal/api/clusters.go:101`; admin only).
5. **Scaling.**
   - No watch; every refresh is a full cluster-wide List.
   - `refreshData()` re-runs every query on each mutation.
   - `src/shared/Table.tsx:64` renders every row; no virtual list.
6. **Minor problems.**
   - Query parameters are not encoded in `src/data/api/index.ts`.
   - `docs/backend.md` describes the old Node proxy.
   - The capability table in the README says "local helm/kubectl binary".
7. **Noticed later.**
   - The Monaco editor loads from a CDN, so the YAML view does not work in an offline installation.
   - The SQLite `foreign_keys` pragma is not enabled; `ON DELETE CASCADE` does not work, and records of deleted users or clusters are left behind.

## 4. Proposed roadmap

This roadmap was turned into the v0.5 design: [`../design-v0.5.md`](../design-v0.5.md).

- **Phase 0, trust:** items 1, 3, 4 and 6; then per-cluster roles or a read-only mode, and an audit log.
- **Phase 1, parity in daily work:** WebSocket PTY terminal and live log streaming; YAML editing with dry-run, diff and conflict warning; generic delete; node cordon/drain/taint; rollout history and undo.
- **Phase 2, shared watch cache:** an informer per cluster, pushed to the UI over SSE/WebSocket.
- **Phase 3, distinguishing features:** security audit (accepted risks in SQLite), RBAC "who-can", topology, Helm install and upgrade with dry-run, cluster comparison.
- **Phase 4, optional:** a server-side AI assistant. Composer is not recommended.
- **Not to be copied:** WSL, local terminal, auto-updater, font files, local binary and tool management.
